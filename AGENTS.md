This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.

## Stack

- Rust binary crate (`offcut`), edition 2024.
- CLI parsing via `clap` with the `derive` feature (`src/main.rs`). Subcommands are optional (`Option<Subcommand>`); running with no subcommand runs the interactive clean flow for each cleanable project. Each subcommand is one of: `list` (read-only project listing, sorted by status), `config` (resolves config — preserves the original list-of-config behavior), `clean` (destructive interactive flow), `discovery`, `classification`, `ignore`, `safelist`, `init` (creates a pre-populated TOML config — issue #25, `src/main.rs::run_init`).
- Config is TOML loaded in `src/config.rs` (`serde` + `toml`), cross-platform config dir via the `dirs` crate. A missing file at the *default* path falls back to `Config::default()`, but an explicit `--config` path that does not exist is a hard error (enforced in `main::load_cli_config`, shared by every subcommand that loads config, not in `config`). CLI flags merge on top via `Config::apply_overrides`.
- Color crate: `owo-colors` in `Cargo.toml`, owned by `src/output.rs`. The rich terminal UI is also owned by `src/output.rs` (workspace table, clean review, blocked state, nothing-to-reclaim state, success panel) and `src/progress.rs` (live spinner lines). Rich UI is gated on a capable TTY (`TERM=dumb` is plain); piped/redirected stdout stays line-oriented for scripts. Color rides the *same* capability gate (`output::color_enabled_with` composes `terminal_ui_enabled_with`) — a stream that gets the plain layout never gets escape sequences with it, so never re-split the two — and `NO_COLOR` (any value) / `CLICOLOR=0` additionally disable color on a capable TTY. Legacy Windows conhost limitation (no VT enabling) is documented in `README.md`.
- Every rendered line — panel, table row, or a standalone status line `main.rs` prints between them — is bounded to the terminal width at *any* width — a tested invariant (the `EXTREME_WIDTHS` sweeps in `src/output.rs`), not a nicety. `main.rs` never formats a bounded line itself: a line carrying a project path goes through `output::format_path_line`, a prose line through `output::wrap_line`, so the budgeting has one owner. A new line must wrap (`wrap_plain`/`wrap_styled`) or truncate its body, **and** split the width with its fixed prefix through `prefix_budget`: a key/bullet/indent emitted at full length is what overruns a terminal narrower than the prefix itself (`COLUMNS=6` reaches it). The one deliberate exception is `pack_columns`, which gives an over-wide entry its own line rather than dropping it — the table footer and legend rely on that. The width fallback chain (`terminal_size` → `COLUMNS` → 80) has one implementation, `progress::terminal_width`; `output::terminal_width` is its presentation-side name. Narrow terminals degrade instead of wrapping: the workspace table stacks below 84 columns, the clean review below `REVIEW_COLUMNAR_MIN_W`.
- Which panel a targeted `offcut clean <PROJECT_PATH>` ends on is `output::blocks_cleaning`, not "is it cleanable": a blocking tree state gets `format_blocked_project` (refuse + the action that unblocks it + `main::blocked_reclaim`'s figure, measured for that one project only and from `Safe` items alone — a blocked project's `Surfaced` items are the user's untracked work, which the demanded commit turns into tracked files offcut will never delete), `Clean` gets `format_nothing_to_reclaim`, and a `Cleanable` project whose inspection failed gets the plain summary line (`main::targeted_outcome_panel`). Never route `Clean` to the refusal — it tells a committed, pushed project to commit and push. `Clean` means no *unprotected* untracked junk, not an empty tree, so that panel's copy must not claim no build output was found: `.offcutignore`-protected `node_modules` is exactly what leaves a project `Clean`.

## Config surface

- User-facing config docs (file location, TOML keys, defaults, CLI flags) live in `README.md`; the resolution logic is `config::default_config_path`. Output formatting lives in `src/output.rs`.
- Top-level flags (`--workspace`, `--config`, `--force`, `--dry-run`, `--verbose`, `--json`) are clap `global = true`, so each is accepted *before or after* the subcommand (`offcut --force list` and `offcut list --force` are equivalent). Do not drop `global = true` — the regression suite is `tests/global_flags_cli.rs`. The `init` subcommand's positional is named `workspace_path` (with `value_name = "WORKSPACE"`) precisely because the global `--workspace` flag would otherwise collide with a positional named `workspace`; do not rename it back.
- `--force` and `--dry-run` may be combined (the #8 flow removed the old clap `conflicts_with`; do not re-add it): `--force --dry-run` previews the force run. Precedence lives in one place each — `dry_run` alone gates execution, `force` alone gates prompting/auto-approval — do not add further runtime precedence logic. Regression test: `clean_force_dry_run_auto_approves_each_item` in `tests/clean_cli.rs`.
- `--json` is a global flag that switches a result-producing command to one machine-readable JSON document on stdout. Schema, per-command shapes, and exit behavior live in `docs/json-output.md`; the emitter is `src/json.rs`; the dispatch is `main::run_json` + the `json_*` functions. `output::set_json_mode`/`output::json_mode` is the process-wide gate that suppresses the rich terminal UI, color, and live progress so stdout carries only the document — never re-split a human `println!` into the JSON path; route through `run_json`. `--json` never prompts and never broadens deletion authority: `clean --json` with neither `--force` nor `--dry-run` returns `approval_required: true` (ok=false, result present), deletes nothing, and exits `3` (`EXIT_APPROVAL_REQUIRED`). Exit codes: 0 success/no-op, 1 error, 3 approval-required — `3` (not `2`) is deliberate so it is distinct from clap's own usage-error exit `2`, which fires before `--json` is known and emits no JSON document. `approval_required` in `json_clean` is computed AFTER the sizing loop from whether any cleanable row survived sizing with items (`any_actionable_cleanable`), not from the raw classification pass — a cleanable project whose safe set/dry-run failed is reported with status + empty items and the run is a no-op (exit 0), mirroring `run_cleaning`'s `cleanable_items.is_empty()` check; do not recompute it from raw status. Regression suites: `tests/json_cli.rs`, `tests/review_fixes_cli.rs`. The `discovery::discover` empty-workspace-roots hint `println!` is gated on `!output::json_mode()` — keep it gated.
- `offcut list` is the read-only project listing command; `offcut config` is the resolved-config command (preserves the original list-of-config behavior). `offcut` (no subcommand) and `offcut clean` each run the full interactive clean flow — sorted report, each cleanable project enumerated and cleaned. `offcut clean <PROJECT_PATH>` scopes discovery and deletion strictly to the named project via `discovery::discover_single`, which bypasses the workspace-root walk entirely (no neighboring project is discovered or cleaned); the user-facing semantics — path resolution, the root-only requirement, `--workspace` being ignored with a one-line stderr notice, nested repos, error cases — live in `README.md` "Project-path targeting" and are not duplicated here. Two sharp edges: the root check (`discovery::git_show_prefix`, i.e. `git rev-parse --show-prefix`, which is empty iff the target IS the worktree root) is defense-in-depth, not the sole guard — `classify::status_no_git` already refuses a subdirectory (no `.git` of its own means `no-git`, which is never cleanable), so do not "simplify" `status_no_git` on the assumption that the root check is what protects subdirectories; and do not "simplify" the root check back into a `git_root != resolved` string comparison against `--show-toplevel`: that false-rejects a real root on a case-insensitive volume (macOS default), where the caller's typed case survives `canonicalize` but `--show-toplevel` returns the on-disk case. `enclosing_git_root` (`--show-toplevel`) survives only to name the enclosing root in the rejection error; it and the target both resolve through the shared `resolve_path` helper (canonicalize, else the lexical `normalized_absolute` fallback) so the two paths in that error keep the same shape. Regression tests: `clean_project_path_*` in `tests/clean_cli.rs`, `discover_single_*` and `normalized_absolute_*` in `src/discovery.rs`. `offcut discovery` finds projects (issue #5 — see `src/discovery.rs`); `offcut classification` classifies them (issue #6 — see `src/classify.rs`); `offcut ignore` and `offcut safelist` are debug hooks for the matcher and the safe-to-delete catalog; `offcut init <path>` creates a TOML config file pre-populated with each `Config` field's default and the given workspace root active (issue #25 — see `src/main.rs::run_init`); a global `--workspace` flag combined with `init` is a no-op and emits the same one-line stderr ignored-notice as `clean <PROJECT_PATH> --workspace` (both human and JSON paths); all eight subcommands are documented in `README.md`.

## Safe-to-delete catalog

- The catalog reuses the `.offcutignore` gitignore matcher rather than its own glob logic, so pattern semantics are the ignore matcher's semantics. Extend the catalog by editing `BUILT_IN_DEFAULTS` in `src/safelist.rs`, never by adding a second matching path.
- `safe_delete` in `Config` **extends** (never replaces) the built-in list. This is the contract users rely on; the regression test is `config_addition_is_recognized_as_safe` in `src/safelist.rs`.
- The catalog is also discovery's single source of truth for artifact-directory descent pruning (`discovery::build_prune_set` — single-segment `**/<name>` or bare-name entries only); never add a second hardcoded artifact list. Semantics owner: `src/discovery.rs` module docs.
- Owners: `README.md` for the user-facing catalog and the `offcut safelist` helper; `src/safelist.rs` module docs and rustdoc for matching semantics and constructor contracts. Unit tests live in `src/safelist.rs`, CLI-level tests in `tests/safelist_cli.rs`.

## Ignore matcher

- `.offcutignore` is gitignore semantics, not a bespoke format: a global
  `~/.offcutignore` plus per-folder files, deepest layer winning. Reach for
  gitignore behavior when in doubt rather than inventing offcut-specific rules.
- `is_ignored == true` means **protected**: cleaning must never act on that path.
  This is the matcher's whole contract with the cleaning engine (`src/clean.rs`).
- Owners: `README.md` for scopes, pattern syntax, precedence, and the
  `offcut ignore` helper; the `src/ignore.rs` module docs and rustdoc for the
  implementation sharp edges and constructor contracts.

## Classification

- `src/classify.rs` shells out to `git` plumbing (`git -C <project> ...`), consistent with the rest of the crate; it deliberately does NOT pull in `git2`. Status precedence is evaluated in order 1→5 (most-severe first); only status 5 (`Cleanable`) is cleanable. The `Clean` state is committed+pushed with NO untracked non-offcutignored junk.
- Status 5 vs Clean uses `git ls-files --others` WITHOUT `--exclude-standard`, deliberately: build junk like `node_modules`/`target/` is gitignored by the *project*, but offcut exists to clean it, so gitignored files must stay visible. The offcutignore matcher (issue #3 `is_ignored`) is the sole judge of whether untracked junk is protected. Owners: `README.md` classification table; `src/classify.rs` module docs; tests in `src/classify.rs` and `tests/classification_cli.rs`.

## Cleaning

- `src/clean.rs` shells out to `git` plumbing (no `git2`), consistent with the rest of the crate. Enumerate untracked with `git ls-files --others --directory -z` **without** `--exclude-standard` (project-gitignored build junk must stay visible so offcut can clean it; `.offcutignore` is the sole protection judge) and **without** `--no-empty-directory` (empty untracked dirs are deliberately enumerated so they are classified rather than silently deleted by `git clean -xfd`).
- Exclusions passed to `git clean -xfd -e` are one root-anchored, glob-escaped literal `/<rel_path>` per protected item plus per un-approved surfaced item — NOT the `.offcutignore` source patterns verbatim. Re-using a nested layer's `/foo` pattern verbatim would exclude `<root>/foo` instead of `<root>/sub/foo`; anchoring each exclusion at the root is what makes nested layers correct. The original zshrc only read global+root ignore files so it never hit this.
- Granularity (from #6 review): a directory that is protected or safe is recorded once; a directory that is neither is re-listed at file granularity so content patterns (e.g. `*.js`) inside untracked directories still protect their files. `git ls-files --others -z -- <dir>` yields full repo-relative paths — use them directly, do not re-join onto `dir`. That re-listing yields files only, so it is paired with an on-disk walk (`discover_fileless_dirs`) that classifies nested file-less directories — otherwise `git clean -xfd` would silently delete them.
- Deferred #3 findings resolved here: `is_ignored == false` for a `!`-whitelisted path means NOT protected (deletable subject to safe-list + approval); an absolute path on the cleaning path is classified `Protected` (fail-safe toward not-deleting, never fail-open) before the matcher is consulted.
- Every question the user answers is asked exactly once, by `src/interactive.rs`, on stderr. The review rendering (`output::format_clean_review`) is deliberately question-free and is printed immediately before the prompt it belongs to; `run_cleaning` re-prints it on stdout only for runs that never showed one, with each item's real fate. Whether one was shown is a fact the flow reports per project (`ProjectResult::review_shown`), not something the caller predicts from the flags: a declined all-cleanup prompt skips the per-project report entirely, and assuming otherwise leaves that outcome with no project path and no item listing on either stream. Do not add a prompt string to a formatter — a second copy on another stream reads as offcut asking and answering for itself.
- Public API seam driven by the interactive flow (#8, `src/interactive.rs`): `clean(project, ignore_set, safe_set, approved, force, dry_run)` and `dry_run(...)`; `build_exclusions` is the exclusion-list builder. The `offcut clean` CLI hook is **destructive**: it deletes via `clean()` only for a project the user approved (or under `--force`), and never under `--dry-run`. Each subcommand — `offcut` (no subcommand, the default run) and `offcut clean` — runs the destructive interactive flow; `offcut list` only lists statuses.
- Owners: `README.md` "Cleaning" section; `src/clean.rs` module docs and rustdoc; unit tests in `src/clean.rs`, CLI-level tests in `tests/clean_cli.rs`.

## Live progress indicator

- `src/progress.rs` owns the live progress writer: `ProgressWriter<W: Write>` is generic over any writer so tests can inject a `Vec<u8>` buffer. TTY-gated via `output::stdout_terminal_ui_enabled()`; `update_discovery(...)` renders the capable-terminal scanning panel (current path, activity bar, scanned-dir count, found-project count, indexed bytes from walked entries, and a bounded six-row recent-project list with marker labels). Extremely narrow terminals degrade to the single `<spinner> walking: <truncated path>` line. `update_phase(phase, idx, total, path)` writes `<spinner> <phase> N/M: <truncated path>` as a single live line (`classifying`/`sizing`/`reading`/`cleaning` counted labels); `clear()` erases the live display in place with no newline — call it before any `println!`/`eprintln!` while a display is live, or padded/cursor-controlled output can linger on screen; `finish()` clears and emits a newline. Terminal width: `terminal_size` crate first, then `COLUMNS` env var, then default 80. Paths are truncated with a leading ellipsis so the leaf stays visible; every rendered panel row is width-bounded.
- Integrated into `src/discovery.rs`: `discover()` constructs a `ProgressWriter::new(std::io::stdout())`, threads it through each `walk_root` call, and calls `finish()` once the walk ends — on success after all roots and on a `walk_root` error before returning it, so no partial progress display lingers ahead of the error. Every subcommand that runs the walk (`offcut discovery`, `offcut list`, `offcut classification`, the default run / `offcut clean`) gets the indicator automatically — no per-subcommand wiring. `offcut clean <PROJECT_PATH>` goes through `discover_single`, which has no walk to report on, so it renders no walking panel; the counted phases below still render.
- Classification, sizing, reading, and cleaning phases: `main.rs::classify_projects` is the single shared classify-with-progress loop (used by `run_listing`, `run_classification`, `run_cleaning`) rendering `classifying N/M`; do not re-inline per-caller copies. The sizing loops in `run_listing` and `run_cleaning` each render `sizing N/M` around each cleanable project's `dry_run` + `compute_reclaimable_size` (single-pass — see "Disk savings" below). `main.rs::render_workspace_table` is the single shared rich-table renderer (used by `run_listing` and `run_cleaning`); it renders `reading N/M` around the per-project `git` calls that fill the BRANCH/CHANGED columns — do not re-inline a second copy of the table assembly, and do not run those `git` calls outside a progress phase. The clean execution loop in `run_cleaning` renders `cleaning N/M` around the actual `clean::clean` call and `clear()`s before each interleaved per-project output block.
- Unit tests in `src/progress.rs` inject a buffer instead of a real terminal — no real TTYs are spawned; see that module's `tests` for the covered cases (TTY gating, scanning panel content/list bounding, truncation incl. multibyte paths and tiny widths, overwrite, clear, finish). CLI-level progress tests preserve piped/plain discovery output.
- Owners: `README.md` "Discovery" section; `src/progress.rs` module docs and rustdoc; the `walk_root` rustdoc in `src/discovery.rs`; unit tests in `src/progress.rs`, CLI-level tests in `tests/progress_cli.rs`.

## Disk savings (issue #18)

- `src/disk.rs` computes per-project reclaimable size (each cleanable project's `Safe` + `Surfaced` items summed via `WalkDir`; file sizes via `fs::metadata` — `stat`, O(1) per file, contents never read; `symlink_metadata` for symlinks; tolerant of permission-denied paths and non-UTF-8 names).
- `src/output.rs` owns the display shape: `format_project_row` carries an optional size on each cleanable row (`path — cleanable (~2.3 GB)`); non-cleanable rows carry no size. `format_summary` carries an optional cleanable-count and an optional aggregate size (`listing: N project(s), M cleanable, ~X reclaimable`).
- Single-pass sizing in `run_listing` and `run_cleaning`: per-project bytes are stored in `per_project_bytes: Vec<Option<u64>>` alongside `per_project_size: Vec<Option<String>>`; the aggregate `total_reclaimable` is the sum of those already-computed bytes, so `dry_run` and `compute_reclaimable_size` each run exactly once per cleanable project. No second walk for the total. `run_cleaning`'s sizing pass additionally stashes each cleanable project's items and safe set in index-keyed side vectors; the report loop `take()`s them instead of re-running `SafeSet::from_config` and `dry_run`, so a project that failed during sizing is skipped consistently in both passes.
- `--dry-run` shows the same sizes without deleting anything; the computation reuses `clean::dry_run`.
- The post-clean success panel reports what the run actually freed, not what was offered: when the user declined a surfaced item, `run_cleaning` re-measures over `would_delete` only (before `clean::clean` deletes the paths), and reuses the sizing pass's figure when nothing was declined.
- Sizes are human-readable (KB / MB / GB, 1024-based, ≥ 1.0 picks each unit) and approximate (the `~` form). The walk does not follow symlinks; each symlink counts its own size only. Permission-denied paths contribute 0, not an abort.
- Tests: unit tests in `src/disk.rs` and `src/output.rs`; integration tests in `tests/clean_cli.rs` verify the rendered output.
- Owners: `README.md` "Disk savings" section; `src/disk.rs` module docs; `src/output.rs` formatting contract; `src/main.rs` `run_listing` / `run_cleaning` callers.
